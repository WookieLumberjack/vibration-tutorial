# vib_tutorial

Real-time teaching app for an N-mass spring-damper chain (PySide6 + pyqtgraph + NumPy/SciPy), managed with uv.

- Run: `uv run vib-tutorial`. Test: `uv run pytest` (GUI smoke test runs headless via `QT_QPA_PLATFORM=offscreen`). pytest runs in up to 4 xdist workers (`addopts`). Each GUI test's windows are freed after it: conftest's `free_windows` (the GUI modules' autouse fixtures) runs `close_graphics`, which also blocks their signals so `gc` freeing a page doesn't call into it half gone, collects, and fails the test if a window it built is still alive or a slot raised (Qt only prints that). A lambda, `partial` or closure over `self` connected to a signal keeps its window for good (PySide holds it as long as the sender, which the window owns): connect a bound method, or `weak.slot(self, lambda self, ...: ...)` (`gui/weak.py`; `tests/test_weak.py` checks `gui/` has none). Drop a window inside a test only after `close_graphics`: freed with its plots still in their scenes, it segfaults. Tests that only build, read or set up pages take conftest's `main_window` (shown, its frame loop held still). A new lesson page goes in `test_lesson_pages_trials_and_tabs`'s list. The run's summary gives each worker's peak address space (`VmPeak`) and warns past 80 % of `ulimit -v`. Pass `-n0` to debug a test in one process. A test that builds a QApplication is marked `gui` (conftest marks the ones using `app`, `main_window` or `free_windows`; mark others by hand, or the unmarked run fails them): a core test over 10 s is marked `slow`, and `-m "not gui and not slow"` is the quick loop (~30 s). The CI doesn't run the suite on PRs (only the release builds do), so run the whole suite before pushing.
- Style: `uv run ruff check` and `uv run ruff format` (config in `pyproject.toml`; the CI's *Lint* workflow checks both, and `cargo fmt --check` and `cargo clippy -- -D warnings` on `native/`). The ignored rules are deliberate (capital matrices, Unicode maths, Qt's camelCase); keep to them rather than adding `noqa`s. The format commit is in `.git-blame-ignore-revs`. Types: `uv run mypy` checks the whole package (the CI too), which is clean: keep it so, with no per-module exceptions. pyqtgraph has no types (it's `Any`). An attribute a page works out later (`self.record = None`) is typed `X | None`, and the code that draws it asserts it's set and why (`assert self.record is not None, "drawn after recompute"`), or a getter makes it (`deriving`'s `_ride()`). `QApplication.instance()` is `theming.application()`, a form's label is `Form.label`, a header's tooltip is `layouts.header_tip`. Don't name a control after a QWidget method (`self.width`, `self.height`, `self.window`): it hides the method from Python callers (`body_width`, `time_window`). What the main window calls on the pages it builds is spelled out as protocols in `main_window.py` (`Themed`, `ChainPage`, `PracticePage`, `SpecPage`). `.pre-commit-config.yaml` runs ruff and mypy before each commit (`uvx pre-commit install`). A dataclass field that `__post_init__` fills in is typed as what it becomes (`ChainSystem.friction`); narrow an Optional with a local and an `assert` saying why it's set.
- A page's notes are brought to #218's quality bar one page per PR (its *Page quality scorecard*; Single oscillator, #229, is the model): every equation in `<eq>` and inline maths in `<m>`, the trials' notes too (M); a figure wherever the text describes geometry no plot shows (P1); a `<notation>` table listing every symbol the page uses, from `notation.SYMBOLS`, a letter doing one job per page, Euler's e upright (P2/P3); the page's gaps filled (P4); a worked example on the page's defaults that matches its readouts, every number in `test_tutorial_numbers.py` from the rounded figures it quotes too, each tied to the notes by `quoted("<notes>", "<number>")` (`tests/notes_quoting.py`; any test module may call it, so a number a page's own tests work out is tied there) (the module's docstring; `test_every_quoted_number_is_checked` fails on a decimal or percentage no call ties that `tests/notes_unchecked_numbers.txt` doesn't list, so take a page's numbers off that list when it's touched) (P5); Further reading with editions checked, a verified citation for each result named after someone, and non-standard figures checked against a source or flagged in the PR (P6). The PR description scores the page; #218's row is updated when it merges.
- `src/vib_tutorial/core/` is NumPy/SciPy with no Qt imports; keep it that way so it stays testable and scriptable. So is the course's data in `gui/` (`links`, the `*_trials` modules, `style`, …) and the notes' figures and maths as SVG (`figures`, every `*_figures`, `maths`; a label's width from `font_metrics`, regenerated by `scripts/font_metrics.py`; Qt draws them in `notes_render`): `tests/test_qt_free.py` imports both in a fresh interpreter and fails on any Qt; a Qt part goes elsewhere (`notes_view.wire` follows `links`' links in a browser).
- **Rebuilding a page: #478's page standard** (the issue holds it in full and the reasons; this is what to build to). A page is rebuilt once, to all of it, and only when its turn comes: don't retrofit a page that isn't being rebuilt (Things to try's place included), so no page is edited twice.
  1. Its body is on screen and runs live, stepped (a `stepping.Stepper`, FOH where linear), not a response worked out in advance and played back; each time history shows the thing it's the displacement of. The Single oscillator is the model: `view_models/live_mass.py` (the run, its pluck, drive and energy books), `grips.py`, `free_body.py` and `recorder.py` (the parts the next pages reuse), `gui/live_body.py` (the body drawn), `gui/free_body_view.py` (its forces), `bindings.py`, and `TrialBox(ask_after_play=True)`.
  2. What's hidden is drawn on the body: forces as a live free-body diagram, frames, the centre of mass, offsets. A diagram that would move with the body goes beside it on the body held still (`free_body_view`): a row a force, its symbol and size in one column on the left where they never move, the body a slim outline, only its arrows turning and growing, sized to the last few seconds' peak (on the moving body its labels jumped sides and couldn't be read; on a square mass the diagram outgrew the body).
  3. The first plot of a kind (an FRF, transmissibility, a spectrum, a PSD) the reader builds from the live run, by dwelling or sweeping, before a later page shows many.
  4. Discovery comes from handling the system, not from a task: m, k, c (friction, the drive, the base) change while it runs, on the drawn body by a grip and in the boxes, and the motion carries on by the physics (`Simulator.set_system`'s rules: a capture keeps momentum, a spring change books ½Δk·x², each jump its own term in the energy balance; never smoothed to look right). The trace keeps what came before, with the change marked. No Apply, nothing hidden in a trial or a tab. **Things to try comes after the system**, not first in the controls: the page opens on its system, and its trials are setups to go back to. **Predictions come after play**, about a case the reader hasn't tried; a prompt is an invitation, never a gate, and no text gives a result away before the reader could have seen it.
  5. It builds on the last page's system and says so in one line (what it builds on, what it's needed for).
  6. One goal: about 8 controls in view, at most 3 tabs plus Theory, 5–8 trials.
  7. The view-model template: state, trials and problems in a Qt-free module; one pure function per panel (`view_models/`); controls bound declaratively, so Defaults round-trips by construction.
  8. Its notes meet #218's bar (above), revised with the page.
  9. Ready for another front end: it joins `tests/test_readiness.py`'s `READY` (its notes' Qt-free module named in `links.NOTES_MODULES`): its state, trials and problems survive JSON (`core/plain.py`'s `to_plain`/`from_plain`), its view model returns plain data (`plain.impure`: colours as theme roles' names), and its notes live in a Qt-free module, so they gather without Qt (`qt_free_notes`) and export as static HTML (`scripts/export_notes.py`). Its interaction logic (what a live change keeps, how a grip's drag maps to m, k, c, the plot recorder) is in its view model, not in Qt handlers.
- `src/vib_tutorial/view_models/` is what a page shows (curves, markers, ranges, readout texts) worked out from its trial dataclass with no Qt, one function per panel or tab; the widget only binds controls → trial → view → `setData`/`setText`, picking colours from the theme. Numbers print through `view_models/text.py` (`fmt` with its SI prefixes, `number`, `plain`, `fixed`, `entry`: one rule for trailing zeros, and no e-notation: 12,300 and 4.62×10⁻⁷), not a page's own formatter; in an f-string that's `{sig(x, 4)}` (`number as sig`), never `{x:.4g}`, which prints 1.23e+04 once x is large (`test_no_page_prints_with_a_g_or_e_format_code`; SVG, LaTeX and CSV keep theirs). Isolation and Duffing are the pilots (their trials or setup live there too; a running page's measured record, `duffing.Record`, too, while the frame loop stays the page's); a page gets one when next worked on. `tests/test_view_models.py` checks the package loads no Qt and ties readouts to the notes with `quoted`.
- Rust kernels live in `native/kernels/` (`vib-kernels`: plain Rust, no PyO3 or numpy, so they build for WebAssembly too; the CI builds them for `wasm32-unknown-unknown` and runs their `cargo test`), with `native/src/lib.rs` the thin PyO3 binding over them (abi3: it converts arrays, releases the GIL and raises a kernel's shape `Err` as ValueError), built by maturin (the package's build backend) into `vib_tutorial._native`; `uv sync`/`uv run` rebuild it when the Rust changes. Put the numerics in the kernel crate, never in the binding. Each kernel replaces a Python function that stays as the reference: `core/native.py`'s `kernel(name, reference)` picks the Rust one when it's built, `VIB_NATIVE=0` runs the Python everywhere, and `tests/test_native.py` compares the two. Name the Python `<name>_reference` and keep the public name for the dispatch (`fluid_bearing.pi_film`). Declare each kernel in `src/vib_tutorial/_native.pyi`, which types the calls for mypy (a test checks it names what the module has); call a kernel class through `core/native.py`'s re-export (`native.LinearSteps`), not `native.module.…`, which mypy can't see into. The release builds' `--smoke-test` fails if the module didn't load.
- `src/vib_tutorial/gui/` holds the Qt widgets. `main_window.py` holds the pages and what spans them (the chain the pages follow, Defaults, the Theory and Practice windows, theme, present mode, keys); `simulation_page.py`'s `SimulationPage` is the Simulation page, which owns the chain and wires its panels to `Simulator`.
- A module's docstring says how it works and, under *Working on it*, what to keep and which tests check it (the rotor's: `core/rotor.py`, `rotor_modes.py`, `rotor_simulator.py`; the films' and the rub's are the simulator's). Read it before changing the module, and keep it up to date there, not here.
- `gui.run()` opens on the page last shown (`open_start_page`: `_on_page_changed` keeps its name in the settings, `LAST_PAGE`), the first time on the course's first page (`open_first_page`, from `links.COURSE`), whose Theory starts with the course map; a bare `MainWindow()` shows the Simulation page, so tests and screenshots build no lazy page. A page once built stays built (its state is kept as the reader left it, and coming back is instant): the window with the Simulation page takes ~170 MB, all 41 pages ~710 MB (measured 2026-11-16; the largest: Random vibration +76 MB, its long records; the Jeffcott rotor +40; OMA +30; the first page after the Simulation page also pays the scientific modules' one-time load). That's the trade made (#316 E8): don't free pages to save memory without measuring a need, since rebuilding costs up to a second and loses the page's state. The *Theory window* (`gui/theory_window.py`, Ctrl+F1, built when first opened) shows any page's notes without building the page: `notes_pages.page_html` (Qt-free) reads the page module's `NOTES_HTML` or `THEORY_HTML` (or `BACKGROUND_HTML`), so keep a page's Theory in one of those, the same as its tab shows (a test compares them). `scripts/export_notes.py OUT` writes every page's notes as static HTML with their equations and figures as SVG (`gui/notes_export.py`, no Qt drawing). Its search box (Find: ⌘F or Ctrl+F, from a page too, `MainWindow.find_in_notes`) indexes those notes' text by section, and the *Glossary of symbols* (its first entry) lists every symbol in `gui/notation.py`'s `SYMBOLS` with a `page:` link to where each comes in: add a symbol there when a page brings in a new one (a letter with a second meaning gets a row of its own). The notes' text lives in `src/vib_tutorial/theory/<module>.html` (packaged by maturin and the spec's `datas`), read by `links.load_notes(name, **parts)`: Qt's rich text plus `<before>` (the page: links to read first) and `<takeaways>` (an `<li>` each), `<eq>` (a display equation in raw LaTeX, typeset by ziamath: `gui/maths.py`; keep each under 360 px, a test checks) and `<m>` (inline maths, set in the bundled STIX Two Text with its variables in italic), `<notation>keys</notation>` (the page's symbol table, from `notation.SYMBOLS`) and `<cite>`/`<reading>` (its *Further reading*, from `gui/references.py`), which it writes out, and `<!--PART-->` markers it fills with what the code works out (`trials=trials_html(TRIALS)`, the course map); write new notes there, not in Python strings (a section another page includes gets its own file and a part: `deriving_pendulum`); headings without an anchor get one for its contents tree. Its `page:` links stay in it. A figure is `<img src="fig:name">`, drawn in the theme's colours by the page's figure module (`gui/<page>_figures.py`, its `FIGURES` dict), which the page passes to the notes that show it, `load_notes(..., figures=<page>_figures.FIGURES)` (`gui/figures.py` has the primitives and the house style; a label's sub- and superscripts are `<sub>`/`<sup>` in `fig.text`, as Qt's SVG ignores a tspan's shift; `test_every_theory_tab_fits_a_1280_px_window` checks every page's notes need no sideways scroll, ~360 px figures). Show notes in a `notes_view.NotesBrowser` (`lesson.theory`), which draws the equations and figures and redraws them on a theme change (a test checks every page's Theory is one).
- Units are SI throughout (kg, N/m, N·s/m, m, N, Hz in UI / rad/s internally where named `omega`).
- The simulator uses an exact FOH matrix-exponential discretization. Don't replace it with an explicit integrator, because stiff user inputs must stay stable.
- The main window's pages are a `PageGroups` (`gui/tab_groups.py`): the groups and their order come from `gui/links.py`'s `COURSE`, the order they're meant to be read in (each page uses only ideas from the pages before it). It mirrors QTabWidget's API over the flat order, so `w.pages.setCurrentWidget(page)` works across groups. Theory notes link to each other with `page:<attribute>#<anchor>` (`MainWindow.go_to`); every page's notes end with `links.next_html` ("Next: … →", a `NotesBrowser.footer` on its tab, appended by `page_html` in the Theory window), and Ctrl+PgDown/PgUp step through `links.order()`; a notes file's `<before>` becomes its "Before this page" line (only earlier pages; `links.before`) and `<takeaways>` its closing list (`links.takeaways`). `links.PATHS` are shorter ways through the course, shown under the first page's map (with each page's problems solved, `practice.progress()`, redrawn as the notes show): each holds every page its pages build on, which `tests/test_links.py` checks, as it checks every link lands on an `<a name>`, every page has both, and a link in the prose to a later page says so in its sentence ("later", "ahead", "next"): it's a pointer, and the page mustn't lean on it. A page's notes may open with `<goals page="…">` (*On this page you'll*), an `<li trial="n" problem="key">` per goal, whose links set up its Thing to try n and ask its problem (`notes_view.ACTIONS`, `MainWindow.act`; `test_links` checks they exist). A trial may carry `predict=Prediction(prompt, choices, answer, why=...)` (`core/practice.py`), which its `TrialBox(..., predictions=...)` asks before setting it up, its note then the explanation (`load_trial` from code skips it); `why` gives a reason for each wrong choice, shown when it's picked (`tests/test_practice.py` checks every one has them), and the Theory tab lists such a trial by its question alone (its note gives the answer away). A question whose answer is a place on a plot is a `Placement` instead (a level or a time, the page's plot by name, its span and a reason for a guess too low or too high): the reader drags a line there, and the guess stays on the plot beside the result (a few One oscillator trials so far). The One oscillator pages have both so far. A page's one-click *Things to try* is a `TRIALS` tuple (its notes may use `<m>`, set by `maths.markup` wherever they show) (the Simulation page's in `gui/sim_trials.py`) whose notes the Theory tab lists too, picked from a `lesson.TrialCombo` (numbered as the Theory's list, keeps the pick shown, a re-pick sets it up again; tests pick by name with `pick`), laid out in a `lesson.TrialSteps` (◂ ▸ beside it, and Alt+PgUp/PgDown on the page showing, step through them in order; presenting with the controls folded, `gui/trial_overlay.py` shows the step's note large); a trial that changes the chain emits `system_requested` rather than setting it, and `tests/test_tutorial_numbers.py` checks the numbers its note quotes. A trial's setup (a `TrialBox` pick, a challenge's or a practice problem's setup, Defaults) runs in a `gui/coalesce.py` `batch()`: mark a page's outermost redraw `@coalesce.coalesced` and it draws once, at the setup's end, with the whole trial loaded, however many of its changes asked for it (a `Deferred` tab too); `tests/test_trial_redraws.py` holds each page to its `BUDGET` of redraws a trial.
- The window fits a 1280 px screen (`test_window_fits_a_1280_px_screen`; 1159 offscreen): it's as wide as its widest page, and a page as its splitter's panes' minimums together. So don't put a long row of controls in a QHBoxLayout (its minimum is the sum of theirs): use `gui/layouts.py`'s `FlowLayout`, which wraps, with `group(...)` keeping a label with its control. Parameter panes and tall panels are `ColumnScroll`s (up and down only, as narrow as their contents allow; give their plots `plot_height`, or they scroll where the plots could have shrunk). A combo box with long items gets `AdjustToMinimumContentsLengthWithIcon`. A table's columns are a `layouts.FitColumns` (each its contents' width, the rest shared out), not Qt's `Stretch`, which split the width evenly and cut the wide cells short (a test checks). Build forms with `layouts.form_layout` (fields fill their column: macOS's default keeps them at their size hint, and such a combo then shows a letter or two). The app's text is the bundled IBM Plex Sans at 12 logical px on every platform (`notes_render.UI_FONT`, `UI_PX`, set by `notes_render.install` from `make_app` and `MainWindow`), so a layout measures the same on Linux, macOS and Windows; regenerate `gui/font_metrics.py` (`scripts/font_metrics.py`) if it changes. Check a layout change with the window at 1280×800, not just 1700×900; a page whose right-hand tabs need more room than `three_panes`' default gives them takes `sizes=lesson.TAB_ROOM` (`test_every_pages_tabs_fit_a_1280_px_window_without_scroll_arrows`). The *Size* box (presenter mode, `gui/display_size.py`) scales it all by Qt's scale factor at launch, so lay out for 100 % only; F5 (`gui/present.py`) folds every page's side panes (its outermost horizontal splitter's first and last) away for presenting, so keep a page's controls and tabs in such a splitter (`three_panes`; `tests/test_present.py` checks every page has one).
- The *Practice window* (`gui/practice.py`, Ctrl+F2, built when first opened) asks each page's `PROBLEMS` (a tuple next to its `TRIALS`, `core/practice.py`'s `Problem`s; `practice.pages()` finds them in the course's order, importing the page modules without building the pages). A problem's `make(rng)` gives a `Question` with new numbers each time: print its inputs round and work the answer from them as printed, with the page's own `core` functions, so the key can't drift from the page. A number is right within a relative `tolerance` (`check` names the usual slips: 2π, 1000, 2, √2); a choice's options are shuffled by `Problem.question`, with its `why` (a reason for each wrong one, shown when it's picked; every choice has them, a test checks). A problem's `figure` (a `fig:` of its page's notes) is drawn above its question. `setup` is the page's trial fields, applied by the page's `load_setup` (`SdofTrial("", "", **setup)`): with `predict` it's offered once answered, and checking runs it on the page. Hints link `page:` anchors (opened in the Theory window; a test checks they exist). A *spec* (`goal`, `design`) is answered on the page: the reader tunes its controls and *Check* passes the page's `practice_state()` (its settings as its trial dataclass, so a goal works without the page) to `goal`, which returns `Requirement`s (`at_most`, `kept`: a spec's given numbers must stay put, or moving them would be a way round it); `setup` is where the tuning starts, `design` settings that meet it (a test checks both through the page's boxes, and that the start doesn't). A page with problems has `load_setup` (and `practice_state` for specs), so its trial needs a field for each control they set or read (`TransientTrial.mass`, not a constant in `apply_trial`). A page's trials, problems and Defaults share one state type: its trials are instances of it, and a field a trial leaves to the chain is `None` there (`shock.ShockSetup`'s duration: `duration_for` the chain's modes), worked out by the page's one `_load`. Where a page's trials aren't its state yet (the rotor's, torsional's, Duffing's and continuum's presets, the coupling page's `CouplingTrial`), a setup dataclass holds what its problems set and read, named by the module's `PRACTICE_SETUP` (`rotor.RotorSetup`) so the tests can build its state. The Simulation page's trials and problems sit in `gui/sim_trials.py`: `SimTrial` takes a chain element by element (`masses`, `springs`, `dampers`, built by `sim_trials.chain`) and the force (`target`, `freq_hz`, `force`); `SimulationPage.apply_trial` sets it up (`load_setup` from a setup) and `practice_state` reads it back, as any page's. A page may show its specs as challenges, `gui/challenge.py`'s `ChallengeBox` under its Things to try (Isolation, Quarter-car, Active control, Frame builder, Rotor so far): picking one loads its `setup`, and while it shows it reads `practice_state()` four times a second and runs `goal` when it changed (keep a goal under ~10 ms), marking it solved (`practice.mark_solved`); Defaults clears it. Solved problems are kept in QSettings (`practice/solved`), and the trials tried and predictions answered beside them (`gui/progress.py`: a page's Things to try tick them, its goals tick once tried and solved, the course map counts them, and an answered prediction's note shows again in the Theory's list; `NotesBrowser` marks any notes it shows); GUI tests that touch it point QSettings at a temporary directory. `tests/test_practice.py` checks every problem over 50 seeds, and that the short cuts its solutions offer (δ/2π, Δf/2f<sub>n</sub>, 15.76/√δ) pass.
- Lesson pages share `gui/lesson.py` (`plot`, `Form`, `TrialBox`, `RunButton`, `fmt`): a `TRIALS` tuple, tabs drawn only when shown, their own `core/` module and a `tests/test_<module>.py`, their notes' numbers in `tests/test_tutorial_numbers.py`, and listed in `test_lesson_pages_trials_and_tabs`. A page with its own model sets `follows_chain = False`; one that follows the chain sends its trials' chains by `system_requested`. The small ones (the One oscillator group but the live Single oscillator, Signals & spectra) have no frame loop: a control change works the plots out at once, in closed form or by `foh.respond` (the exact FOH update, as the chain's, in Rust where it's built; `foh.free` with no input). A control change whose work takes more than ~100 ms goes through a `gui/recompute.py` `Recompute` (debounced, on a worker thread, the latest result only; `now(job)` for trials, Defaults and new chains, which the reader waits for and tests read at once; `wait()` in tests): the job is a pure function built from the controls' values, touching no widget (the Nonlinearity page's sweep). A value the reader can drag on a plot is a `gui/drag.py` `DragLine` (a line with a grip, in data units on a log axis too) or `DragDot` (a dot snapping along a path: a pole along a root locus), or a `DragPoint` (free: `dragged(x, y)`, the page clamps it and `place`s it; the Single oscillator's poles); bind its `dragged(value)` to the page's box (a bound method) and move it with `set_value`/`place` when the box changes; call its `apply_theme()` from the page's (`tests/test_drag.py` drags them with synthetic mouse events). A small page's closed-form response is played back in time by a `gui/playback.py` `Playback` (Start/Pause, Reset, speed, a time cursor that scrubs; `moved(t)` places the page's body, `set_span` on each redraw, `play()` from a trial or a pluck) until its rebuild makes it live (#478; the Single oscillator steps a `view_models/live_mass.LiveMass` in a `FrameLoop`): Pendulums' `PendulumView`, Vibration isolation's `IsolationView`, and the Quarter-car's `QuarterCarView` (the car over its road). A curve of more than ~10 points a pixel is decimated by `plots.py`'s policy (its docstring): x increasing, `decimate(plot)`; a path, `thin`; the live strip chart, `Decimator`. Use `PlotDataItem(pen=None, symbol=…)` for markers on a log axis: a `ScatterPlotItem` ignores the log mode. Every control needs a name a screen reader can read: `Form.add`, `layouts.form_row` and `layouts.group` name theirs from their labels (`gui/accessible.py`); a control built outside them gets a buddy label or `setAccessibleName`. A plot is named after its title or axes when its page is built (`accessible.name_plots`); one with neither (a drawing: the chain, the rotor) gets `setAccessibleName` where it's made (`tests/test_accessible.py` checks every page's controls and plots).
- The strip chart (`TimeHistoryPlot`) decimates incrementally: `Decimator` caches each curve's own min/max per bucket (a bucket per pixel column of the plot, so the line covers the pixels the whole record would) by absolute sample number (`History.offset`), and `update_data` gets a `values(index)` callback so only new and decimated rows are derived. If the plotted values of samples already seen change (other curves, a new modal map), go through `set_curves`, which resets the cache.
- The Simulation page's history keeps every stride-th step (`_store_stride`: samples STORE_DT apart, or STORE_PER_PERIOD to the fastest mode's or forcing's period, `Simulator.fastest_hz`, or a tenth of a pulse), continuing the stride across advances (`_carry`). The presets keep every step; a stiff chain's 7.6 µs steps keep every 4th, so the 300,000 samples span ~9 s, not 2.3. Everything recorded per sample (energies, element forces) is worked out only for the kept ones; the energy balance still closes on them.
- `Simulator.advance` caps the number of steps per call (`MAX_STEPS_PER_ADVANCE`). Loop over it for long runs in tests. The Simulation page also caps each frame's steps to its compute budget (`FRAME_BUDGET` over the measured cost of a step, `PROBE_STEPS` while a new system's isn't known), so a test that wants a set stretch of simulated time from `_tick` should call `sim.advance` itself.
- BLAS runs on one thread (`vib_tutorial.main` sets `OPENBLAS_NUM_THREADS` and friends before NumPy loads, and the worker always): the matrices are small, and OpenBLAS's pool made the cracked shaft's frames 6× slower. Measure before letting BLAS thread again.
- A page's motion has one control, `lesson.RunButton` (Start, then Pause / Resume; Space while its page shows, through `panels.space_bar`: a button's own `setShortcut` is reset by `setText`), beside a Reset back to t = 0 at rest. The window's run bar (`gui/transport.py` `TransportBar`, along its foot) drives whichever motion the page and tab showing have: a page gives it with `transport()` (a `Transport` of its run, reset, speed and clock, or None; it may depend on the tab), or gets its one `Playback`'s (`tests/test_transport.py`). A page that simulates a response (Duffing, Rotor, Gyroscope, the Waves tab, Torsional's start-up, Deriving's release, the mounts' and the frame's forced response) opens at rest and waits for Start; a mode shape swings on its own. A trial (or a practice setup) starts it; a control neither starts nor stops it (a page that relaunches on a change keeps the run state). The Simulation page is the model: its force (Space) is its Start. Paused, a page that simulates as it runs (Simulation, Duffing, Torsional's start-up, the rotor) shows a `gui/scrub.py` `Scrub` on its time plots: dragged back, the page draws its body from what it recorded at that instant (`scrubbed(t)`); Start hides it and carries on from the pause (`tests/test_scrub.py`). The app's keys are listed once, in `links.KEYS`: the first page's *How a page works* (`<!--KEYS-->`) and the About box show it, and every page's first show (ever) opens its Theory tab at the top (`MainWindow.introduce_pages`, which `gui.run()` turns on; a bare `MainWindow` doesn't), so the first run opens on that page's *Start here*. Add a new shortcut there; a test checks the main window's are all in it.
- `gui/frame_stats.py` is the frame-timing overlay (`VIB_FRAME_STATS=1`, or a CSV path to log too). Every page's frame loop runs inside `frame_stats.frame(page, sim_t, target_ms)` (free when it's off), and `MainWindow.event` times each repaint; a new page's loop is a `gui/frame_loop.py` `FrameLoop` (given the page's bound methods: `tick(dt)`, `runs()`, `sim_t()`), which does this for it: it starts its next frame `FRAME_MS` after this one began (not after it ended: that adds the frame's work to every interval), ends it with `gui.settle_plots(page)`, and stops while the page is hidden (every page's loop is one, the Simulation page's included, but the virtual modal test's, which paces a measurement; `loop.enabled = False` holds one still for a test) (it applies the plots' new ranges in the frame: pyqtgraph defers them to the paint, which then dirties the items and paints every rescaling plot twice). Don't touch a plot's items in a frame where nothing on it changed (the Bode marker at a steady speed): any change repaints its axes and grid. The CSV also has `view` rows (what shows: the tabs picked, a page's `frame_context()`, window size, scale, Hz) and `input` rows (`InputLog`, an app-wide event filter: the control's label and new value); `scripts/frame_report.py` cuts a log at them and summarizes each stretch. Give a new page a `frame_context()` if what it shows isn't in its tabs (the rotor's preset).
- Every page's plots get `gui/plot_export.py`'s right-click menu when the page is built (copy or save its curves as CSV, save a PNG, show all, hold its curves in grey to compare and clear them), in place of pyqtgraph's; held curves survive the page's `setData` and `clear()` redraws, and Defaults clears them; a view whose class handles `mousePressEvent` itself (an editing canvas) keeps its own right-click. A legend is made with `theming.add_legend`, which keeps it off the data (`gui/legend_place.py`: the plot's clearest corner, or above the plot where none is; `test_no_legend_hides_data` checks every tab); one made by hand over a plot calls `legend_place.follow`.
- *Defaults* (`MainWindow.restore_defaults`, Ctrl+R) puts the page showing back as it first showed: its `practice_state()` then (`_opening`, read in `_on_page_changed`: a page may settle its controls as it shows) through `load_setup` (less the trial's name, note and tab), and for a page that follows the chain the chain it showed with (`_opening_chain`); then its Reset if it had started, and its `TrialCombo`s back at the prompt. So a page's `practice_state` must round-trip through `load_setup` (`tests/test_defaults.py` checks every page after its last trial or preset).
- `gui/plot_patches.py` (installed by `make_app`) changes every pyqtgraph plot: a grid is drawn opaque, in the colour its translucent lines would have had over the background, and its axis sits behind the ViewBox so the lines pass under the data (the translucent grid was ~35 ms a frame on a plot that rescales: the Duffing page ran at 20 fps, 47 now). A centred `LabelItem` (a title) wraps to the width it's given instead of setting its plot's minimum width (long titles made plots overflow their view at 1280 px). The patch only reads the label's own state: asking for its parent while a scene is torn down segfaulted. For a marker that moves every frame use `lesson.Dot` (an ellipse moved with `setPos`), not a one-point `ScatterPlotItem` (~0.2 ms a `setData`), and don't re-range a plot each frame for a small change (`OrbitPlots`' `RESCALE`, `plots.SteadyRange` for a live plot's axis). A plot whose curves stay still while something moves over them (a time cursor, a playhead, a body's marker) is held, `plot_patches.hold_still(plot)` (each curve drawn from a pixmap; `Playback.add_cursor` does it): otherwise every frame strokes them all again (37 ms on the Single oscillator). Don't hold a plot whose curves change every frame. A text a frame loop rewrites every frame is a `lesson.LiveLabel`, not a QLabel, whose `setText` lays the page out again each time (6.5 ms a frame on the Waves tab).
- Colours come from the theme in `gui/style.py` (the Projector theme also scales every pen's width and marker's size, `line_scale`/`marker_scale`, through `plot_patches`' `mkPen` and `ScatterPlotItem.setSize`: so make pens with `pg.mkPen` when the page draws or takes a theme), read at draw time through `colors` (`colors.mass[i]`, `colors.force`, `colors.muted`). Don't hard-code a colour: it has to be legible in every theme (`style.contrast` gives the WCAG ratio; aim for 3:1 for curves, 4.5:1 for text). A widget that keeps pens or brushes across redraws needs an `apply_theme()`, called from `MainWindow._restyle`. Mute secondary labels with `theming.mute`, not a stylesheet colour. The first four mass colours stay apart for red-green colour-blind eyes too (no green beside a red), and mode 1 apart from `strong`: `tests/test_style.py` checks every theme.
- To check UI changes, grab a screenshot offscreen: run the script with `QT_QPA_PLATFORM=offscreen` (only the tests set it; without it the window opens on the real display and gets resized by the compositor). Create the app with `gui.make_app("Light")` (or another theme name); `gui.run()` uses the theme last picked, which is stored in the user's settings. This sets Qt's palette and pyqtgraph's background (the default is black). Then build `MainWindow`, resize it to 1700×900 (the README screenshots' size), run the event loop briefly, and `window.grab().save(path)`. Check a change in Light and Dark at least; `MainWindow.set_theme(name)` switches live. The README's and docs/' images come from `scripts/readme_screenshots.py` (saved as 256-colour PNGs, `write_png`, a third of full colour's size); rerun it (or just the affected shots) after a visible UI change and check the captions' numbers still hold (they're in `docs/`). `tests/test_scripts.py` runs every shot (no waits, no PNGs) and sets up `scripts/mac_timings.py`'s scenarios, so a refactor that breaks them fails the suite.
- The README is the overview and the contents; each course group has a page in `docs/` (`docs/<group>.md`, from `links.COURSE`'s group names) with a `##` section per page in the course's order, plus `the-window.md`, `the-math.md` and `code-layout.md`. A new page goes in `COURSE` and, by the module and class that build it, in `links.PAGE_CLASSES` (the one page registry: the main window builds it from there and makes `window.<attribute>`); it gets a section in its group's page and a line in the README's Contents (its summary from `COURSE`); `tests/test_docs.py` checks both, and that every relative link and anchor lands.
- Releases: pushing a `v*` tag that matches `pyproject.toml`'s version runs `.github/workflows/release.yml`, which builds unsigned PyInstaller apps (`packaging/vib-tutorial.spec`) on Linux, Windows and macOS, launches each with `--smoke-test`, and publishes them as a GitHub Release. Build locally with `uv run --group build pyinstaller packaging/vib-tutorial.spec`. If a new feature imports a Qt module, check the spec's `EXCLUDES` and `DROP` lists don't remove it. To try the builds on a branch, `gh workflow run release.yml --ref <branch>` (merges only build when they touch the packaging or dependencies).
- pyqtgraph views left in a scene until interpreter exit can segfault in PySide's teardown (exit 139 *after* pytest prints "passed"). `gui.close_graphics(widget)` tears them down; `gui.run()` and the GUI tests' autouse fixture call it. Check the exit code, not just the summary line.
- Don't let Qt delete a layout item behind PySide's back (e.g. `setParent(None)` on a widget in a layout, which `PlotWidget.close()` does). PySide wraps the items of a filled layout added to another, never learns of the deletion, and a new QObject at the reused address then resolves to the stale wrapper: intermittent segfaults, seen on macOS in `QMenu.addAction`. Take the item out with `layout.takeAt()` first, as `close_graphics` does.
